# Design spec

This is the current best design for the data model, the prompt-assembly rules and the command surface. It is a living document, not a contract. The **hard rules** below are fixed. Field names, shapes and mechanics are suggestions that explain the intent. If implementation shows a better way, change it, update this file in the same commit, and say why in your report.

## Vocabulary

| Term | Meaning |
|---|---|
| **User** | A local login. Has a username and an optional password. With a password, all of that user's data on disk is encrypted. With an empty password, it is plain JSON (for debugging). |
| **Conversation** | One chat or one campaign ("D&D at the Gilded Goat", "Pathfinder, dark and gritty"). Owns its settings, templates, setup messages, brains and ledger. The UI may call it a campaign; the code calls it a conversation. |
| **Brain** | A named AI persona inside a conversation (Game Master, Dice Master, Joke Teller, Scene Painter). Each has its own system prompt, an optional final reminder, and a kind (`text` or `image`). Exactly one is the **default brain**. |
| **Ledger** | The single shared, ordered list of messages in a conversation. Every brain sees the same ledger, from its own point of view. Editing a ledger message changes what every brain sees. |
| **Setup messages** | Ordered text blocks (World Bible, Module, ...) sent verbatim, each as its own message with the role it is set to (`user` by default, `assistant` or `system`; T13), to every brain right after its system prompt. |
| **Templates** | Conversation-level framing strings (the HTML-comment wrappers) used when one brain sees a message from the player or from another brain. They are plain editable text. |
| **Steer** | A one-off, behind-the-scenes direction used when regenerating the latest brain message. It is sent once and never appears in any later prompt. |
| **Fresh take** | The other way to regenerate (T15, reshaped in T17): your idea for the reply goes into the ledger as a **note from the Muse**, a hidden note right before the message, and the brain answers it, never seeing the reply it replaces. The new version is the reply alone. |
| **Muse** | T17: the brain called Muse, which writes a fresh take's notes (your words, never generated). A brain like any other; the first fresh take adds it when the conversation has none. Every brain reads its notes framed `<!-- from: Muse -->`; the player sees them folded. |
| **Roll** | A d20 the server rolls (never a model), added to the ledger as a player message that every brain reads (T09, "Dice rolls"). |
| **Pin** | A ledger message pinned to a brain (T16): in that brain's requests it is sent right after the setup messages instead of at its place, as it stands now (a live link, not a copy). Every other brain still sees it where it is. |
| **Maker** | A brain with the setting "Each new message makes a new brain" (T16, `makes`): every new message it gets makes a brain from its **blueprint**, named from its pattern (`Character {{n}}`), with that message pinned to it. The app knows nothing of what the made brains are for. |

## Hard rules

1. **No hidden text.** Every string we send to a model comes from user-editable fields: system prompts, setup messages, templates, final reminders, tool descriptions, tool-result text, ledger content and steer text. Code must never add prose, instructions or wrappers of its own.
   - Venice must always get `venice_parameters.include_venice_system_prompt: false`. Without it, Venice adds its own system prompt.
   - `prompt.preview` must return the **exact** request body that would be sent (minus the auth header). The real send path must use the same function, so preview and reality cannot drift. A test asserts this.
   - The only text outside our control is the model's own chat template (how DeepSeek serializes the tool schema). That is unavoidable and is noted in the UI's payload view.
   - **Never send a request without a user-written system message (Jason, 2026-10-14).** Some Venice models (confirmed: `venice-uncensored-1-2`, found by T01 QA-1) insert their own built-in prompt of ~550 tokens ("you are uncensored…") whenever a request has no non-empty system message, even with `include_venice_system_prompt: false`. Any non-empty system message suppresses it. So a brain's system prompt must be non-empty: brain create and update reject an empty one, and the send path refuses, with a clear error, to send a body whose first message isn't a non-empty `role: system`. `prompt.preview` shows the same error. Jason's words: "The system prompt should be whatever we put in, and nothing else." 
2. **Terminal-first.** Every capability is a registered command. The web UI only calls commands. There are no UI-only endpoints.
3. **Local only.** The server binds to `127.0.0.1`. Nothing is deployed and nothing is pushed.
4. **Never put reasoning text or steer text into a prompt.** They are stored for display only. (A fresh take's `thought` field is display only too. T17: its words reach prompts only as the Muse's note, a ledger message of its own that the user can edit, re-version or delete like any message. T15 versions still carry theirs at the head of their content, saved merged.)

## Storage layout (flat files, gitignored)

```
data/
  users/<username>/
    user.json                     # plaintext metadata only: username, encrypted flag, KDF params + salt, wrapped data key. Never the password or a raw key.
    conversations/<convId>.json   # whole conversation document (encrypted users: binary ciphertext, see below)
    images/<imageId>.<ext>        # image bytes. Plaintext users: ext is the type sniffed from the bytes (T05).
                                  # Encrypted users: ciphertext, always .bin (T06: the type hinted at the model)
  users/.deleted-<username>-<hex>/  # only while user.delete removes a folder (renamed away first; never listed)
.run/                             # gitignored runtime state: server.pid, server.log, cli-session.json, mock pid
```

- Writes are atomic: write a temp file, then rename.
- The server keeps no cache it could not rebuild. Every command loads from disk and saves to disk. That way the CLI, the browser and a restarted server always agree.
- One generation at a time per conversation. A second `turn` or `regenerate` on a busy conversation returns a 409 error. An image is not part of it: since T05 triage an image is a job of its own once its prompt is saved, so the next brain can go while it is made (see "Image generation").

### Encryption

- Key derivation: `scrypt(password, salt)` → 32-byte key-encryption key (node:crypto, N = 2^17, r = 8, p = 1, about 200 ms). The salt and params go in `user.json`.
  - **Bounded (T06 QA-5).** The params come from a file anyone at the computer can edit, and scrypt runs them as given: `N = 2^24` made one login allocate 16 GiB and swap the Mac for minutes. `checkKdf` (crypto.ts) refuses, before anything runs, params that aren't positive integers with N a power of two, or that cost more than 8× the defaults in memory (1 GiB) or work (~1.6 s). That leaves room to raise `KDF_DEFAULTS` later. `loadUser` checks every `user.json` this way, and checks its shape and its username; a bad one is an `unreadable_file` error that says so ("damaged: …, so X can't log in"), `user.list` lists it apart under "damaged", and `user.delete` can still remove it.
- **Envelope (implemented in T01, replacing the planned verifier):** each encrypted user has a random 32-byte *data key* that encrypts their files. `user.json` stores only `wrappedKey`, the data key encrypted with the scrypt key in the file format below. A wrong password fails the GCM check on `wrappedKey`, so no separate verifier is needed, and a future password change only rewraps one small blob instead of re-encrypting every file. Never store the password or a raw key.
- File format: magic `SSENC1` + 12-byte random IV + 16-byte GCM tag + AES-256-GCM ciphertext, with the magic as GCM additional data. Use a fresh IV on every write.
- All user-file access goes through `src/storage/vault.ts` (`readJson` / `writeJson` / `readBytes` / `writeBytes` / `removeFile` / `listFiles` on a `Vault = {dir, key}`), which encrypts when the session has a key. It refuses plaintext files in an encrypted user's folder (and vice versa), refuses paths that escape the user's folder, and never touches `user.json`. Temp files from atomic writes are already ciphertext.
  - Vault files always live in a subfolder (`conversations/`, `images/`), and any `.` or `..` path segment is refused outright. So no spelling reaches `user.json`: macOS volumes are case-insensitive, so a name check alone would let `USER.json` or `conversations/../user.json` through (T01 QA-3).
  - `readJson` replaces `JSON.parse`'s error with a plain "not valid JSON": V8's message quotes the text it failed on, and internal errors are logged, so a corrupt file would otherwise put decrypted content in `.run/server.log` (T02).
  - A vault can be **closed** (`closeVault`): the key buffer is zeroed and every later read or write throws `session_ended`. As a last-ditch guard, `encrypt()` refuses an all-zero key.
  - **A file it can't read is a 500 `unreadable_file` that names the file and why (T06 QA-2)**, never "Internal server error": can't be decrypted with this user's key (damaged, or another user's), cut short (it starts with `SSENC1` but is shorter than the header), empty, not encrypted in an encrypted user's folder, encrypted in a plaintext user's folder, not valid JSON. The message never quotes content, so it is safe to show and the log keeps only the code. `conversation.list` lists such files as unreadable and shows the rest. Nothing is written over one: every write loads first.
  - **A conversation file must hold the conversation its name says (T06 QA-4)**: `loadConversation` checks `conv.id`. A copy of another conversation under a second name would otherwise list twice and take that name's writes. Ciphertext isn't bound to its file name (GCM additional data is just the magic): swapping or restoring one's own files needs write access and reveals nothing, so the id check is enough here. A swapped image file would show the other picture.
- Everything under the user's dir except `user.json` is encrypted, images included. Titles too, since they live in the conversation doc.
- **Image file names are neutral for encrypted users (T06, T05 QA-6):** `images/<id>.bin`. A typed extension (`.webp`, `.png`) gave away the format Venice returned, which hints at the model. Nothing needs it: the record has `mime`, and `readImageFile` sniffs the decrypted bytes (so does `settleStaleImages` when it recovers a crashed image). Names from before T06 are still found, and `auth.login` renames an encrypted user's to `.bin` (names only, nothing decrypted). Plaintext users keep typed names, so their images open in a viewer.
- The key lives only in server memory, in the session. A server restart means logging in again.
- Never log message content, prompts or image bytes to `.run/server.log`. The server logs only method, path, status and timing, plus error codes, and for a failed chat request a record without its words ("Diagnosing a failed chat request"). A successful `auth.whoami` or `health` isn't logged at all (T07 frontend): a visible browser tab asks both every 30 s, which was two lines a minute per window; their failures still are.
- Every `/api` response carries `Cache-Control: no-store`, so the browser never writes decrypted conversations or images to its disk cache.
- **The password is never stored, nor anything it can be read back from.** `user.json` holds a random salt, the scrypt parameters and `wrappedKey`: the data key encrypted under `scrypt(password, salt)`. That is "hashed and salted" in effect: the only way to test a guess is a full scrypt run (~200 ms, 128 MB) per guess.
- **Password change (T06, `user.change-password`)** is cheap because of the envelope: unwrap the data key with the current password, rewrap it with the new one under a fresh salt (at today's `KDF_DEFAULTS`), and write `user.json` atomically. No file is re-encrypted. The user is logged out everywhere; work already running finishes. A plaintext user has no password to change, and an encrypted user can't drop its password (that would mean decrypting every file). The data key itself doesn't change, so a copy of `user.json` taken before the change still opens with the old password; real re-keying would mean re-encrypting every file, and isn't built.

### Who is using a user's data right now (T06)

`vault.ts` keeps every open vault of the server, by user folder: each session's master (`openVault`, from `unlockUser`) and each fork (`forkVault`: a request's copy, a paint job's, a stopped reply's drain). `closeVault` takes it out. An open fork is work running on that user's data, so:

- **`user.delete` is refused (409 `user_busy`, nothing deleted) while the user has an open fork**, other than the deleting request's own. The message names what is running when it can (`generatingFor(dir)` in store.ts, `paintingFor(dir)` in images.ts: a reply in `c_…`, an image in `c_…`), else "a request is still using its data". This is the T01 QA-2 fix: running work holds its own key and finishes after logout, and its last save would otherwise bring the folder back with no `user.json`.
- With nothing running, in the same tick as the check (so nothing can start in between): the user's sessions are destroyed and every open copy of its key is closed (`closeVaultsOf`, which marks them `deleted`, so a late use says "This user was deleted" rather than "you logged out"). Then the folder is **renamed** to `users/.deleted-<name>-<hex>` (atomic: the name is free at once, and nothing can log in to it or read it) and removed. Sessions and keys are closed once more after the rename, for a login that finished in between. A removal cut short leaves a dot-folder that nothing lists; the next delete sweeps it.
- **A login that races a delete fails.** `unlockUser` re-reads `user.json` after scrypt (~200 ms) and refuses if the user is gone or was re-created (`createdAt` differs), or if its password changed meanwhile.
- **The vault never creates a user's folder.** `writeBytes` makes only the subfolders below it (`makeParents`, non-recursive) and writes with `writeFileAtomic(..., {makeDirs: false})`, so a write after the folder is gone fails (`session_ended`, "This user was deleted") instead of re-creating `users/<name>/conversations/`. `user.json` writes don't create folders either.
- Any new work that outlives its request must `forkVault` its own copy and `closeVault` it in a `finally` (as before). That is also what makes it visible to `user.delete`.

### Where plaintext can still appear (T06 audit)

Data at rest is ciphertext. These are the other places text can land, and what is done about each:

| Where | Status |
|---|---|
| User folders | Ciphertext, image names neutral. `test/encryption.test.ts` greps for a phrase of every kind (title, system prompt, reminder, setup label and text, brain names and prompts, tool text, template, negative prompt, message, steer, edit, image prompt, words in a brain's mouth, a fresh take's thought and the thought template) and the image bytes, with a plaintext user as the control. |
| Temp files | Atomic-write temp files are ciphertext (the vault encrypts before writing) and live in the same folder. |
| `.run/server.log` | Method, path, status, timing and error codes. Internal errors log a stack, but no error message carries content: Venice errors go to the client only, and `JSON.parse` errors (which quote their input) are replaced. The test asserts it, failures included. **Since 2026-10-20 a failed chat request also logs a record without its words** ("Diagnosing a failed chat request"): ids (conversation, brain, the user as a pseudonym), the model and every knob sent, and **each message's role and size in characters, in order**: metadata, kept on purpose (Jason asked for it), the same kind a file size is. Every string of the request is its length; Venice's error text stays, but masked wherever it repeats the request, and cut at 600 characters. `test/diagnose.test.ts` puts a phrase in every kind of text, fails requests every way, and greps the log. |
| `.run/cli-session.json` | The session token, the username and the URL. The token is useless once the server restarts, the user logs out, or nothing has used the session for the idle limit (60 minutes; see "Sessions"). |
| Server memory | Every logged-in session's data key, and the Venice key. Reachable only through a session (the cookie, or the CLI's token above), which ends after the idle limit, or through a debugger: `npm run up` starts the server with `--disable-sigusr1`, and the server ignores SIGUSR1 itself, so `kill -USR1` can't open Node's inspector on it (T06 QA-1). Anyone who can attach a native debugger to a process of Jason's account is out of scope. |
| Process arguments (`ps`) | `./sst` sets `process.title = "sst"`, which overwrites its arguments on macOS and Linux a few ms after start (tested). `npm run sst --` shows them in npm's own process: use `./sst`. |
| Shell history (`~/.zsh_history`) | What you type on a command line is kept by an interactive shell. The CLI warns when a password is given as a flag, and `auth.login` of an encrypted user says that `--content -` (stdin) keeps text out of the history. Agents' non-interactive shells keep no history, but Claude Code keeps everything an agent does (next row). |
| **Claude Code transcripts** (`~/.claude/projects/-Users-jasonhorsley-code-simple-silver/*.jsonl`) | **The biggest plaintext copy on the Mac (T06 QA-3).** Claude Code saves every command an agent runs and every output it reads, in plain text: decrypted `conversation.get` output, prompts it typed, passwords it piped to `auth.login`. QA found its test phrases and a dev password there. **Mitigation:** agents only ever use `qa-*`/`dev-*` users, whose content is made up (AGENTS.md: they never log in as Jason's users, read or list their folders, or reuse a CLI session they didn't create), and nothing in the app hands an agent Jason's data unasked. **Residual risk:** if Jason himself asks Claude Code to look at, debug or play in one of his real campaigns, that text lands in a transcript in the clear, readable by anyone with his account, until Claude Code's cleanup removes it (`cleanupPeriodDays`, 30 days by default) or he deletes the file. So: debug with a `dev-` user and a copy of the problem, never the real campaign. The app can't encrypt what Claude Code writes. |
| npm's debug logs (`~/.npm/_logs`) | They record each run's full command line. The project `.npmrc` turns them off for this project (`logs-max=0`, with `logs-dir` inside `.run/` so npm's pruning leaves other projects' logs alone). |
| The browser | `/api` answers are `no-store` (tested for JSON, errors, streams and images); localStorage holds only the last username and panel state; URLs and the page title carry ids and "simple silver" only; every content field is `autocomplete="off"`, so Chrome keeps no Autofill history of it. That also keeps its value out of Chrome's session files on disk: T06 QA drove a normal Chrome profile and found a composer draft nowhere on disk, while a control `<textarea>` without the attribute was in `Sessions/` (the DevTools MCP's Chrome writes no session files, so check that with a normal profile). Unsent drafts live in the tab's memory only (`lib/drafts.ts`). |
| Venice | Gets the prompts in plaintext, by nature. The default models are private. |
| What you export | `image.get --out`, `turn > reply.md`, the terminal's scrollback: your choice. **But the app's own suggestion keeps out of the project folder (T07 QA-3):** after an image the CLI used to print `image.get --id img_… --out img_….webp`, which from the repo root wrote a decrypted picture into a folder that git would happily commit. It now prints `image.get --id img_… --open`, a CLI-side flag that writes the copy to the OS's per-user temp folder (`$TMPDIR/simple-silver/<id>.<ext>`, folder 0700, file 0600), opens it in the default viewer and says it is a plaintext copy to delete. `.gitignore` also ignores `/img_*` at the root, and the README says that anything taken out is a plain file. |

What stays visible, by design: usernames, whether a user is encrypted, how many conversations and images it has, file sizes, timestamps and ids.

What the encryption doesn't cover: a session in use. While Jason is logged in, the app shows his campaign to whoever sits at the unlocked Mac, as it must. The idle timeout (below) bounds that to the limit after his last action, and the browser blanks itself when the limit passes; for a shorter absence, lock the screen, use Log out everywhere (the browser's user menu, or `./sst auth.logout --all`: open windows blank within 30 s), or `npm run down`.

### Sessions

- `auth.login` derives the key, then creates a random session token mapped in memory to `{username, key}`.
- The token only ever travels in the `sst_session` cookie (`HttpOnly; SameSite=Strict; Path=/`), never in a response body. The browser keeps it as a cookie. The CLI reads the same `Set-Cookie` header and saves the token in `.run/cli-session.json` (mode 0600), then sends it back as a cookie, so both clients take the identical path. Without the running server's memory, the token is useless.
- When a request carries a token the server no longer accepts, the response has an `x-sst-session` header saying why (T06 frontend): `expired` (the idle limit), `logged-out` (`auth.logout --all` from elsewhere), `password-changed`, `deleted`, or `invalid` for a token it doesn't know (in practice: it restarted). The server remembers the last 200 ended tokens and why (`sessions.ts`, `EndReason`), until it restarts. A command that needs the login gets the same reason as its 401: `session_expired`, or `session_ended` with the reason in words ("dev-x was logged out everywhere (…)", "The password for dev-x was changed…", "This user was deleted…"). The CLI deletes its saved token and says why; the browser drops to the login screen and says why.
- `user.delete` and `user.change-password` log that user out everywhere (T06). The CLI keeps one login per session file; `SST_SESSION_FILE=<path>` gives a terminal its own, so two terminals can be two users side by side.
- Logging in again replaces the caller's previous session. Logging out wipes the key from memory. `auth.logout --all` ends every session of that user (other tabs, other terminals) before you step away.
- **Idle timeout (T06 triage, QA-1).** `npm run up` runs for days, so a login that never ended was the easy way in: the open tab, or `./sst` with the token in `.run/cli-session.json`, for anyone at the Mac. A session nobody has used for **60 minutes** ends, and its key is wiped from memory. `SST_SESSION_IDLE_MINUTES` changes it (in the environment, or a line in `.env` for live mode; fractions work for a quick check by hand; `0` = never). The server logs the setting at startup and `npm run up` prints it.
  - *Used* means a command that needs the login (`auth: true`): sending, editing, opening a conversation or an image. The adapter calls `sessions.touch` after its session check. `auth.whoami`, `health`, `help` and `user.list` don't count, so a client that only looks (the browser's checks) never keeps a session alive.
  - `lookup` ends an idle session the moment a request carries its token; a sweep (every minute, or every quarter of a shorter limit, `unref`ed) ends it when no request comes, so its key doesn't sit in memory. Running work holds its own fork and finishes as with a logout.
  - Clients are told why: a timed-out token gets `x-sst-session: expired` (not `invalid`), and a command that needs the login fails with 401 `session_expired` ("Your session expired: nothing used it for 60 minutes, so the server logged it out and wiped its key from memory."). The server remembers the last 200 ended tokens for that, until it restarts; a later logout --all, password change or delete relabels that user's with the newer reason. The CLI drops its saved token and prints the error plus `Log in again: ./sst auth.login --username <name>`; on a command that doesn't need the login (whoami) it prints a dim line instead.
  - `auth.login` and `auth.whoami` return `idle: {minutes, secondsLeft} | null`, and the CLI prints it ("The session ends after 60 minutes without activity (42 minutes left)…"). The browser uses `secondsLeft` to look again (whoami) when the session would end, so an idle tab drops to the login screen ("You were logged out after 60 minutes without activity…") instead of leaving the campaign on screen.
  - Why 60: about the longest Jason would think, read rules or eat between actions in a session, while short enough that a Mac left unlocked over lunch shows the login screen. Measured from the last *action*, not from login, so a long evening of play never logs him out.
- **Running work keeps its own key (T01 QA-2).** The session holds the master vault. The HTTP adapter gives each request its own copy (`forkVault`) and closes that copy when the request's work is done, after a stream has fully drained. So logout, or logging in again, kills the token and wipes the session's key at once, while a `turn` or image generation that is already running finishes and saves under the real key. It can never write under a wiped key. Work that outlives its request (a detached job) must `forkVault` its own copy and close it when done; a request's vault is closed once the handler returns.

## Conversation document

Implemented in T02 as `src/conversations/types.ts` (the types), `defaults.ts` (new conversations and brains) and `store.ts` (files, write queue, generation lock). The shape below is what is on disk.

```ts
type Conversation = {
  schemaVersion: 7;                    // bump it and upgrade on load if a later ticket changes the shape. 2 (T07 triage): every brain
                                       // has `stop`; loadConversation fills a missing one with defaultStop (upgradeConversation,
                                       // defaults.ts), in memory, and the next write saves it. 3 (T09): templates.roll, filled the same way.
                                       // 4 (T13): every setup message has a `role`; a missing one is "user", as it was always sent.
                                       // 5 (T15): templates.thought, filled with the default. 6 (T16): every brain has `pins`
                                       // (none, in an older file); `makes` and `madeFrom` are optional, so an older file has neither.
                                       // 7 (T17): templates.thought, if it is still T15's default, becomes the Muse's note
                                       // (upgradeTemplates, also run on a campaign import); a changed one is kept. Once only
                                       // (T17 QA-2): a file already at 7, or a campaign file that says schemaVersion >= 7,
                                       // keeps its template, T15's wording too
  id: string; title: string; createdAt: string; updatedAt: string;
  settings: {
    textModel: string;                 // default "deepseek-v4-1-flash"; must be in Venice's /models list (any of it: the
                                       // pickers offer the models in models.ini, see "Models" below).
                                       // T18: the default for its brains: a brain with a textModel of its own uses that
    maxTokens?: number; temperature?: number;   // omitted = not sent
    imageModel: string;                // default "z-image-turbo"; T18: the default for image brains without their own
    image: { resolution?: string; format: "webp" | "png" | "jpeg"; hideWatermark: boolean; negativePrompt?: string };
             // default { format: "webp", hideWatermark: true } (T07: was false; Venice stamped its mark on T05's live image).
             // T05: only what the image model takes is sent (buildImageRequest). The picture's shape is each image
             // brain's own (Brain.shape, 2026-10-14): it was a conversation-wide width/height/aspectRatio, so a
             // portraitist sharing a conversation with a scene painter painted portraits in landscape. On load, those
             // old fields are dropped (upgradeConversation)
  };
  templates: {
    player: string;          // default "<!-- from: the user -->\n{{content}}"
    otherBrainText: string;  // default "<!-- from: {{brain}} -->\n{{content}}"
    otherBrainImage: string; // default "<!-- from: {{brain}}. It called generate_image with this exact prompt: -->\n{{prompt}}"
                             // (T07: it used to add "and that image is now on the player's screen", untrue while it paints or after a failure)
    steer: string;           // default "<!-- Behind-the-scenes direction from the user. This is not part of the conversation. Write your previous response again, following this direction: -->\n{{instruction}}"
    roll: string;            // T09, default "🎲 I rolled a d20: **{{roll}}**": the text of a roll's message, made once, when the server rolls
    thought: string;         // T17, default "```hidden\nAn idea for {{brain}}'s next reply, which the player won't see:\n\n{{thought}}\n```":
                             // what a fresh take's Muse note starts as, the caret at {{thought}}, {{brain}} the brain it is for. A pre-fill:
                             // the request builder never renders it (the note is a ledger message; see "Fresh take"). T15's default was
                             // "```hidden\n{{thought}}\n\nThat sounds good, I'll respond next.\n```" (T15_THOUGHT_TEMPLATE)
  };
  setup: Array<{ id: string; label: string; role: "user" | "assistant" | "system"; content: string }>;
                                       // s_...; the label is for the user only, never sent. role (T13): what it is sent as, default "user"
  brains: Brain[];
  defaultBrainId: string;              // T02: replaces Brain.isDefault, so "exactly one default" holds by construction
  messages: LedgerMessage[];
  spentUsd?: number;                   // T03 triage: what the conversation has cost, and it only grows (see "Cost" below).
                                       // Absent in older files: totalCost() then sums the versions.
};

type Brain = {
  id: string; name: string; color: string;   // name is unique (case-insensitive), never looks like an id (b_...), and is one line of visible text
  kind: "text" | "image";              // cannot change once the brain has messages

Template placeholders are literal string replacements and there are only six: `{{content}}`, `{{brain}}`, `{{prompt}}`, `{{instruction}}`, `{{roll}}` (T09) and `{{thought}}` (T15). Rendering is a **single pass** with a function replacer, so a message that itself contains `{{brain}}` or `$&` is never expanded again. A placeholder a template has no value for (say `{{prompt}}` in the player template) is left as typed, where the preview shows it. Four templates are applied every time a request is built; the `roll` template is applied once, when the server rolls, to make that roll's message (see "Dice rolls"); the `thought` template is a pre-fill for a fresh take's note, rendered by the server only for `message.regenerate --thought --wrap` (see "Fresh take"), with `{{brain}}` the brain the note is for.

**Each template must keep the placeholder its text goes into (T03 QA-3):** `player` and `otherBrainText` need `{{content}}`, `otherBrainImage` needs `{{prompt}}`, `steer` needs `{{instruction}}`, `roll` needs `{{roll}}`, and `thought` needs `{{thought}}` (where the caret goes, and `--wrap` puts your words). `{{brain}}` is optional, and only the two other-brain templates and (T17) `thought` fill it in; in `player` or `steer` it is left as typed. Without it, the text would silently go missing: a blank steer template dropped the steer and left an empty message after the brain's own reply. `conversation.update` refuses such a template, and `buildRequest` refuses to use one (`bad_template`, 400, nothing sent) for files written before the check. The wording is in `templateProblem` (`prompt.ts`). A bare `{{content}}` (no framing at all) is fine.

**Cost (T03 QA-2).** `spentUsd` is what the conversation has cost, and it is what the CLI and the browser show. Each save adds the reply's `cost.usd` (`addSpend`, called before the version goes in, so an older file's total is first pinned from its versions), and the drain adds a stopped reply's cost when Venice reports it (see **stop**). The total never goes down: deleting a message removes it from every prompt, not from the bill. The one cost that can't be counted is a stream that breaks mid-reply: it reports no usage, though Venice probably bills what it wrote. A conversation made by `conversation.clone` or `.import` (T07) starts at `spentUsd: 0`: it hasn't cost anything yet.

**Storage mechanics (T02).** Every change is a read-modify-write of the whole file through `mutateConversation(vault, id, fn)`, which runs one job at a time per conversation. So a rename while a reply streams is not lost when the reply is saved: the reply's save re-reads the file and appends. The generation lock (`beginGeneration`, the 409) is separate from that queue. It carries a stop signal, which `generation.stop` aborts (`stopGeneration`, T03), and the abort for the Venice request, which `release()` fires unless a stop has handed the request to the drain (`keepUpstream`). **While a generation runs, ledger edits are refused too** (`assertLedgerIdle`, T03): `message.edit`, `.delete` and `.select-version` get a 409, because the reply in flight answers the messages as they were sent, and a regenerate's save expects its message to still be there. Stop it, then edit. Title, settings, templates and brains can still change mid-reply. `conversation.delete` is refused while a generation runs.
- **The lock and the read must agree (T03 QA-1).** A "not while generating" check runs *inside* the conversation's queue (in `mutateConversation`'s `fn`), and a generation reads the conversation *through* that queue, after taking the lock: `gen.load()`, never a bare `loadConversation`. So an edit whose check passed a moment before the lock has finished writing by the time the generation reads, and every later edit sees the lock and gets its 409. With a bare read, QA saw a delete land after a regenerate had read the old ledger (the whole reply was generated, billed and then thrown away), and turns that answered pre-edit text. T04's "brain delete, not while a generation for it runs" (`assertBrainIdle`, below) and T05's generating commands follow the same pattern. The lock also keeps, in server memory only, the events the generation has streamed so far (consecutive deltas merged), so `generation.follow` can re-attach to it (T02 frontend). A generating command passes its events through `gen.relay(...)`, which records them and hands followers the same `done` or error the caller gets.
- **Which brain is writing (T04).** A generation says which brain answers right after planning (`gen.forBrain(id)`). `assertBrainIdle` (inside `mutateConversation`, like `assertLedgerIdle`) refuses to delete a brain, or change its kind, while it is writing: its reply isn't in the ledger yet, so the "has it spoken?" check alone would let a delete through, and the save would add a message by a brain that is gone. Between the lock and the plan the brain isn't known yet, so every brain counts as busy for that moment. Other brains can be added, edited and deleted mid-reply, and so can setup messages: the reply answers what was sent.

## Prompt assembly (the heart of the app)

`buildRequest(conversation, targetBrainId, { model, excludeFromMessageId?, steer? })` in `src/conversations/prompt.ts` is a pure function returning the full chat-completions body. The body's `model` is the brain's text model (T18, `textModelOf`: its own, or the conversation's), and `opts.model` is what `/models` says that model can do (reasoning support and effort levels): a lookup by id (`ModelBook`; the command layer's `textModels`, from the cached list, refuses a model Venice doesn't list with `unknown_model`, naming whose model it is) or one model's caps (tests). Caps whose `id` isn't the brain's model are refused, so one model's caps can't shape another's request. A blank `steer` is refused (a caller bug, not "no steer"; T02 QA-5): a plain re-roll passes no steer at all. T02 implements every branch below, image brains and steering included, with unit tests (`test/prompt.test.ts`), so T03-T05 only wire commands to it. T04 checked it end to end with three brains (`test/brains.test.ts`, and live): it needed no change.

**One code path for preview and send.** `planTurn(conv, {brain, content}, model)` (`src/conversations/turn.ts`) builds the would-be player message and the body. `prompt.preview` returns `plan.body`; `turn` sends `plan.body` and saves `plan.player`. A test compares the preview with what the mock received, for the same `--content`. `planRegenerate(conv, {message?, steer?}, model)` (T03) sits beside it: `message.regenerate` sends its body and `prompt.preview --regenerate [--message] [--steer]` returns it, and `test/regenerate.test.ts` compares the two for every steer in the green/blue/green scenario. It also does the checks (last message, brain author) and trims the steer (blank = plain re-roll), so the preview and the send can't disagree about any of it. T15 extends it rather than forking a path: `planRegenerate(conv, {message?, steer?, thought?, wrap?}, model)`, and `prompt.preview --regenerate --thought` returns that body (`test/fresh-take.test.ts` compares it with what the mock received). T17: with a thought it plans the Muse's note too (`planMuseNote`: the note and the Muse, would-be, as `planTurn` plans a player message) and builds the body from the ledger with the note in place, so the builder itself knows nothing of fresh takes.

For the target brain **B**:

1. `{ role: "system", content: B.systemPrompt }`. Always present and never empty; refuse to build otherwise.
2. For each setup message, in order: `{ role: setup.role, content: setup.content }`. Verbatim, no template. Blank ones (whitespace only) are skipped rather than sent empty. **The role is the setup message's own (T13):** `user` (the default, and all there was before T13); `assistant`, which every brain reads as its own words (the same text for every brain: that is the point of a staged exchange, World Bible and house rules as `user`, then "Understood." as `assistant`); or `system`, a second system message where it stands in the order. A system setup message is never merged into step 1's system prompt: a separator would be text the user didn't write. A body that would end with an `assistant` or `system` setup message (no ledger, no reminder) is refused like any other (`nothingToAnswer`).
2b. **Pinned messages (T16):** for each ledger message pinned to B (`B.pins`), in ledger order, what it is sent as (see "Pinned messages"): `ledger` sends exactly what step 3 would send for it at its place; `system` and `assistant` send its active version's text verbatim with that role (skipped when blank, as setup messages are). B's own image message is always sent as the tool call and result it was. Only messages this request's ledger holds count: a regenerate's message, and anything after it, is left out here too, and a steered regenerate keeps the message it revises at its place, right before the steer, even when it is pinned to its own brain.
3. For each ledger message `m`, in order, using `m.versions[m.activeVersion]`, **except those pinned to B** (they went in at 2b). On regenerate, stop before `excludeFromMessageId`:
   - **Player message:** `{ role: "user", content: render(templates.player, {content}) }`.
   - **B's own text message:** `{ role: "assistant", content }`.
   - **B's own image message:** `{ role: "assistant", content: "", tool_calls: [{ id: "call_<m.id>", type: "function", function: { name: B.tool.name, arguments: JSON.stringify({ prompt: content }) } }] }`, followed by `{ role: "tool", tool_call_id: "call_<m.id>", content: B.tool.resultContent }`.
   - **Another brain O's text message:** `{ role: "user", content: render(templates.otherBrainText, {brain: O.name, content}) }`.
   - **Another brain O's image message:** `{ role: "user", content: render(templates.otherBrainImage, {brain: O.name, prompt: content}) }`.
   (T15 had a step 3b here, a fresh take's thought as the brain's own `assistant` words. T17 removed it: the thought is now the Muse's note, an ordinary ledger message at step 3.)
4. If `B.finalReminder.enabled` and its content isn't blank: `{ role: "user", content: B.finalReminder.content }`. Verbatim.
5. If steering: `{ role: "user", content: render(templates.steer, {instruction: steer}) }`. This goes last, so the whole prefix stays cache-friendly.

**Stop sequences (T07 triage, QA-2).** The framing is a pattern a model will continue: live (T07 engineer), after a few framed `<!-- from: Dice Master -->` messages, the GM answered an uncertain action by writing the whole exchange itself, a fake Dice Master line, a fake `<!-- from: the player -->` "I got an 11" and the verdict. Prompts ("never write `<!-- from: ... -->` comments yourself") made it rare, but they are a probability, and they guard only brains whose prompts say so. So every brain has `stop`, and a text brain starts with `["<!-- from:"]`, the default templates' prefix: Venice ends the reply just before such a line, whoever wrote the brain's prompt.
- **It is a request setting, not text sent to the model**, so hard rule 1 holds. It is still plain to see: it is in the body `prompt.preview` returns, the payload view adds a sentence that says what it does (`stopNote`, wording.ts), `brain.list` and `brain.update` print it, and `brain.add` / `brain.update --stop` edit it (repeat the flag; `--stop '[]'` clears it). A campaign file's brains take `stop` too (absent: the kind's default).
- **Image brains start with none.** They answer with a forced tool call, so they can't write a framing line, and a stop inside a prompt would cut the prompt.
- **Older conversations get it on load** (schema 2, above): Jason's existing text brains are guarded from the next request on, and say so in the preview. A list someone emptied stays empty.
- **A reply cut to nothing** (it began with the stop sequence) is saved as an empty reply, as any empty reply is; its `done` note says a stop sequence may have cut it, and suggests a regenerate.
- **With reasoning on, Venice applies stop sequences to the reasoning too** (measured, below): a reasoning brain that thinks about the framing is cut mid-thought, with no reply text. Reasoning is off by default; when it is on and the brain has stop sequences, the payload view and `brain.update` say so (`STOP_REASONING_NOTE`).

## Turns, regeneration and edits

- **turn** `(conversation, brain = default, content?, roll?)`. If `content` is not empty, append a player message and save. With `roll` (T09), the server rolls a d20 and appends it as a second player message, after the text (see "Dice rolls"). Then generate a response from `brain` and append it as a new brain message. With empty content, it just asks the brain to respond. Example: a Character Portraitist whose system prompt says "unless the player asks for someone specific, paint the most recently introduced character". With empty content it does exactly that; with "(paint the barkeep, give him a leather apron)" it follows the note. No special code is needed. The player message is simply framed like any other, and the brain's prompt decides. Refused when the body wouldn't end with a `user` or `tool` message: the brain's own reply last, or only its system prompt (see above).
  - **Order and failure (T02).** Lock (409) → load → plan (empty system prompt or unknown model: 400, nothing saved) → open the Venice stream and wait for its headers (an up-front refusal: 502, nothing saved) → save the player message, emit `message` → `start` → deltas → save the brain message → `done`. If the stream breaks after that, the player message stays, no partial reply is saved, and the stream ends with `error`, whose message says so and that `turn` with no content retries. (A stop is different: what had arrived is kept; see **stop** below.) A client disconnect doesn't stop anything, even one before the first event: the reply finishes and is saved (T02 QA-2). An empty reply (live, `max_tokens` counts reasoning, so a small budget can end inside the reasoning) is saved as it came, and the `done` note says "no reply text" (T02 QA-6); the UI should show an empty bubble as such, and T03's regenerate and delete can replace it.
- **regenerate** `(messageId = the last message, steer? | thought?)`. Only allowed when `messageId` is the **last** ledger message and has a brain author (`not_last_message`, `not_a_brain_message`); the message's own brain writes it. The result becomes a **new version** of the message, appended after the others, and the active one. The steer text is stored on that version for display, with `steeredFrom` (the version it revised). It is never sent again. A steer is trimmed; a blank one means a plain re-roll. For an image brain the new version is a new prompt and a new image (T05): the old version keeps its own image, so the pager goes back to it. That holds while the old version's image is still being made, too (T05 triage): it lands in its own version.
  - **Order and failure (T03, like turn).** Lock (409) → load → plan (refusals: 400, nothing sent) → open the Venice stream → `start` (with `regenerate: true` and the `steer`, so a UI or follower renders it in the message's slot) → deltas → save the new version → `done` with the whole updated message. If the stream breaks, no version is saved and the error says the message keeps its current version.
  - **Without a steer** it is a fresh re-roll: build the request for that message's brain with `excludeFromMessageId: messageId`. If that body then ends with the same brain's own earlier `assistant` message (two of its messages in a row), it is refused with `nothing_to_answer`: `reviewBody` reports it for the preview, and the send path refuses it anyway.
  - **With a steer** (changed in T02, see the live probe above): keep the message in, so its active version is the brain's own last `assistant` message (or tool call), followed by the reminder if any, then the rendered steer. The model needs to see what "your previous response" is. Only this one request carries the old version and the steer; later prompts see only whichever version is active.
  - **Fresh take: with a thought** instead of a steer (both together, or a blank thought, is a 400). Jason's second kind of regenerate: a steer asks, as the user, for a rewrite of the reply on screen; a fresh take gives the brain an idea it then carries out as if it were its own ("The hooded stranger is always an old man. Tired trope. Subvert it: three goblins in a trench coat…"), never seeing the reply it replaces. **T17 reshaped it** (live, T15's thought planted as the brain's own trailing words was a prefill, and broke; see "Prompt assembly"): the idea is **a note from the Muse in the ledger, right before the message, and the brain answers it.** It works the same for any brain: the default one, a Co-GM, a made character, an image brain, with or without a reminder.

The first fresh take adds it when the conversation has none (`newMuse`: a text brain with a pre-filled system prompt, `MUSE_SYSTEM_PROMPT`, the next free color, its reminder on), in the same write as its first note; so does `message.add --as Muse` (and `message.set-author --as Muse`). **Why a brain, not a new kind of author** (the ticket's first guess): framing, `message.add --as`, set-author, pins, delete, versions, campaign files, import and clone, the CLI's views and the browser's brain colors all work for it unchanged, and Jason's first idea, a creativity brain that writes twists itself, is just a turn to it (its system prompt is used only then; a fresh take's note is your text, which no model writes). A brain called Muse that is an image brain is refused, with how to fix it (rename it; a 400 `bad_brain`, since the browser reads every 409 `conflict` as "a reply is being written", T17 QA-3); a fresh take on the Muse's own note is refused (edit it). `brain.update`'s help says what a rename does; nothing warns at the rename itself (T17 QA-4, by design).

If the message right before is already the Muse's note **that you wrote** (a second fresh take, or a note written by hand: its active version is `source: "authored"`), the text becomes **a new, active version of that note** (its own pager), not a second note. A message the Muse *generated* on a turn of its own (its own twist, or a poem from a brain that only happens to be called Muse) is its own and stays: the fresh take's note goes in after it (T17 QA-1: a poet called Muse lost its poem to the note); if that note already says exactly this, it stays as it is and only the reply gets a new version (another roll with the same idea). Jason accepted that the two pagers can disagree: going back to the reply's v2 while the note shows v3's idea is fine. Every brain reads the note at its place from then on (other brains framed, the Muse its own words), so the Co-GM and the painters stay consistent with the twist; delete it and later requests don't have it. A plain re-roll or a steer after a fresh take sends it too, since it is in the ledger.
    - **The request** is a re-roll's (the message left out, so the brain never sees the reply it replaces) built from the ledger with the note in place, then the reminder: it ends on the note or on the reminder, a `user` message whatever the brain. `planRegenerate` plans the note (`planMuseNote`, would-be, nothing saved) the way `planTurn` plans a player message, so `prompt.preview --regenerate --thought` is the request; its `notes` start with `freshTakeNote` (where the note goes, and that a Muse is added when there is none), and `regenerate.note` says the same as data (`{messageId?, version, isNew, same, muse, museCreated}`; a new note's id comes when it is saved). `buildRequest` knows nothing of fresh takes.
    - **The send.** Lock → load → plan → open the Venice stream → **save the note** (and the Muse, if new) in one write, once Venice has taken the request, as a turn saves your message; `muse_note` `{message, before, brain, brainCreated?}` says so, before `start` (insert `message` right before `before`, or replace it by id) → `start` (with `thought`) → the reply streams → the new version (`saveMuseNote`, `src/commands/chat.ts`). A stop mid-reply keeps the partial reply as the new version, as any stop does; a stop before any reply text and a break save no version, and say that the note stays and that a plain regenerate answers it; a break's `details.retry` is that plain re-roll (no thought: sending it again would add it to the note again). A stop before Venice answers saves nothing at all.

Editable like every template, needs `{{thought}}`. Schema 7 swaps T15's untouched default for this one (a changed template is kept); a campaign import does the same.

- **select-version.** Go back to version 2 of 10, decide it's the good one, and keep playing from it. Switching the active version changes what every brain sees from then on. Any message, at any depth. Commands number versions from 1, as the CLI shows them (`--version 2` is `activeVersion: 1`); a steer on the re-selected version revises it, and the result is added as the newest version.
- **edit** `(messageId, content)`. Edits the active version in place (`edited: true`; no change, no flag). Any message can be edited, player or brain, at any depth. Blank text is refused (delete the message instead). For an image message the text is its prompt (T05): saving a new prompt edits it in place and starts a new image from it. The edit answers at once; the image is painted after, as a job of its own (T05 triage), and `image.follow` watches it. While the active version's own image is still being made, its prompt can't be edited (409: it would be replaced before it was ever shown; wait for it to land). The old image stays (as `previous`) until the new one is done, then the new one swaps in and the old file is deleted; if the new one fails, the old one is still shown, beside the error. The same prompt again changes nothing and paints nothing (use `image.retry`).
- **delete** `(messageId)`. Any message, with all its versions. T16: in the same write, every pin of it goes, and a brain made from it (`madeFrom`) goes too while it has never spoken and isn't the default; one that has spoken stays with what it said and only loses the pin. The answer lists `brainsDeleted` and `unpinned` (which brain lost what). Deleting an image message deletes its image files, every version's (T05), after the ledger is saved: a failed removal leaves an unreferenced file, never a message whose image is gone. `conversation.delete` removes all of its images the same way. Both wait for images still being made (T05 triage, 409 `image_busy`): Venice is making and billing them, so they must land somewhere first.
- **stop** `(conversation)` (T03, `generation.stop`). Aborts the running turn or regenerate and returns once it has settled. **What had arrived is kept**, marked `stopped: true`: a turn's partial reply is saved as the brain's message, a regenerate's as a new active version, so it can be edited, regenerated (with a steer, too) or deleted like any reply. Jason sees the text as it streams, so it is his to keep; throwing it away would also leave a turn's player message unanswered, with no reply to regenerate. If no reply text had arrived (still connecting, or only reasoning), nothing is saved and the stream ends with error `stopped` (status 499), whose message says what was kept: a turn keeps only the player message; a regenerate keeps the current version.

Once the prompt is saved, the generation is over (T05 triage): the image is with Venice, being made and billed, and no stop touches it. `generation.stop` then has nothing to stop, and its result lists the conversation's images still being made (`painting: [{messageId, imageId}]`), with `IMAGE_STOP_NOTE` (wording.ts) saying why they are kept. (Until T05 triage a stop waited up to 10 s for the image and then claimed it was "finished and kept" even when it was still pending: T05 QA-3.) A stop whose generation hasn't settled after 10 s says so (`error.code: "still_saving"`).

When the stop arrives, `relayReply` stops relaying at once and returns what had arrived plus the unread rest of the stream. The generation saves it, ends and frees its lock as before. A detached **drain** (`drainStopped` in `src/commands/chat.ts`, on its own `forkVault` key copy) then reads the rest quietly, discards the text, and adds the usage and cost Venice reports at the end to `spentUsd` and to the stopped version, if one was saved. A stop before Venice has answered drains too, once Venice answers. Whether Venice bills that case is unmeasured live; the drain records whatever Venice reports. A stop before anything was sent sends nothing. If the drain's stream breaks, or the conversation is deleted meanwhile, nothing is recorded.
  - **Say so wherever a stop is offered:** "Stopping saves waiting, not money: Venice still writes and bills the whole reply, so its cost is added to the conversation once Venice reports it." That sentence is `STOP_BILL_NOTE`, returned as `generation.stop`'s `note`, so the browser can show the server's own words. A stopped version's cost appears a little after the stop: live, within seconds; on the mock with `MOCK_SLOW`, once the rest of the reply has been sent.

Versions, pins and `madeFrom` are untouched, and it makes no brain. Jason moves the old Character Actor's lines onto each character's new brain with it.

- **Brains** (T04). Add anytime: a brain added mid-campaign sees the whole ledger from its first request (its own replies: none yet; everyone else's: framed). Edit anytime: name, color, system prompt, reasoning, reminder, tool text, safe mode; the next request uses the change. A rename changes the framing everywhere, history included (`<!-- from: {{brain}} -->` uses the current name), as an edit would.   - **Delete** only if no ledger message references the brain (`brain_in_use`, 409), it isn't the default (`default_brain`, 409: set another default first), **and not while it is writing a reply** (`assertBrainIdle`, above). A brain that has spoken stays: every other brain still sees its lines under its name. Rename it or change its prompt instead.

### Diagnosing a failed chat request (2026-10-20)

A chat call can fail with almost nothing to go on (live: a 500 "chat completions inference processing failed" on an always-reasoning model). So a failed `turn`, `message.regenerate` (steer or fresh take) or image brain's prompt call carries **everything about the request but its words** (`src/venice/diagnose.ts`): what failed and when (refused up front with an HTTP status, never answered, or broke mid-stream), Venice's error body and its request-id-style response headers (`x-request-id`, `cf-ray`, `x-venice-*`, rate limits, `date`), the timing (to the answer, to the first chunk, to the failure), what had arrived (chunks, characters of reply, reasoning and tool-call arguments, whether a `finish_reason`, usage or `[DONE]` came), the model with its context length, the reasoning fields actually sent, the other knobs, every message's role and size, flags for anything unusual (the same role twice in a row, a `system` message after the start, a body not ending on `user`, empty content, tool calls without tools or without their result, an estimate near the context), a token estimate (~4 characters a token, labelled as one: there is no tokenizer) and the newest reply in the conversation that worked (its prompt tokens are Venice's own count). Nothing is re-sent to learn more.

- **Built by allowlisting.** `redact` keeps numbers, booleans and a string only under a key known to hold structure (`model`, `role`, `type`, `reasoning_effort`, `enable_web_search`) with that key's shape; every other string becomes `<N chars>`, keys included when they don't look like field names. Tool names, stop sequences and ids are text the user can edit, so they go too. A field added to the request later is redacted until someone adds it to the list.
- **The user's view** is `details.diagnostics` on the error (stream `error` event, or the HTTP error of an up-front refusal), next to `details.retry`. It adds who each message is from (read from its framing, `<!-- from: Dice Master -->`), the brain asked and Venice's whole answer (up to 8000 characters). The CLI prints it as a block under the error (`formatDiagnostics`; `--json` prints the error itself, the diagnostics as data); the browser shows the same text under **Details** in the failed reply, the notice above the composer and the regenerate box, with Copy.
- **The log's view** (`forLog`, in `CommandError.log`, which `logFailure` prints indented under `turn failed: 502 venice_error` and no client ever gets) names nothing: the conversation and brain by id, the user as `u_` and the first 10 hex digits of the username's SHA-256 (`printf %s <name> | shasum -a 256 | cut -c1-10`; the conversation id finds the folder anyway), the request described afresh from the body, so nothing added for the user can come along. **Venice's error text is the main clue, so it stays, masked** (`maskEcho`): any run of 12 characters or more that also occurs in a string of the request, as sent or JSON-escaped (a validation error may quote a message), and any whole string of 6 or more, becomes `[N chars that repeat the request, masked]`; then it is cut at 600 characters. It leans to masking: a phrase of Venice's that the conversation also contains is masked too, which tells the log only that Venice's words were in it. Header values and our own failure sentence go through the same mask.
- The mock answers every chat request with `x-request-id: mock-req-<n>`, and `MOCK_ECHO_ERROR` is a 400 whose error quotes the last message, as a validation error might.

### Image generation

Implemented in T05: `src/conversations/paint.ts` (the job), `images.ts` (who is painting; stale images), `repaint.ts` (retry, edit, add), `tool-call.ts` (the prompt inside the call), `src/images/` (request builder, sniffing, files) and `src/venice/images.ts`.

1. **The prompt.** The image brain's request carries its tool and a forced `tool_choice`. Its argument fragments are kept apart by `index` (two parallel calls used to be glued into invalid JSON, T02 QA-7) and **only the first call is used**; a second one is reported in the `done` note. `parallel_tool_calls: false` is not sent, since no live call has shown Venice honours it. The first call's `prompt` is decoded as it streams and sent as `{type:"prompt", delta}` events: words, not JSON fragments, so the CLI prints the prompt and the browser shows it live. Text the brain writes beside the call is set aside; once 2,000 characters of it have come with no call started, the reply is ended (`IMAGE_TEXT_LIMIT`, T18 QA-2: see "Models", Mistral Small 3.2).
2. **Saving it.** The whole prompt (`JSON.parse` of the arguments) becomes the message's content (or a regenerate's new version), with `image: {status: "pending"}`, and `image_pending` carries the saved message. A prompt that only partly arrived (a stop, or `max_tokens`: `finish_reason: "length"`) is saved too, because it was shown and paid for, but not painted: its image is an `error` that says why, to edit or retry. A reply with no prompt at all (the model answered in text, or called without one) saves nothing and fails like a broken reply (`no_prompt`, 502, with `details.retry`); its cost still goes on the total.
3. **The request.** `buildImageRequest(settings, model, prompt, safeMode, shape)` (pure; `prompt.preview` shows its result for an image brain as `image: {path, params, notes}`; the browser runs it too, to price each image model) makes `{model, prompt, safe_mode, format, hide_watermark, ...}` and sends only what the model takes, from `/models?type=image`. The brain's shape (`SHAPE_SIZES`) goes to a model with an `aspectRatios` list as the listed ratio nearest 2:3, 1:1 or 3:2 (a note says when it isn't exact), and to the rest (z-image-turbo and the other width × height models) as 832×1216, 1024×1024 or 1216×832, rounded down to `widthHeightDivisor`. The conversation's `resolution` goes only to a model that lists it (2026-10-14: a resolution left from another model used to go to a model with no resolution list at all). `negative_prompt` goes when set. Whatever is left out or rounded is said in `notes`. A prompt over the model's `promptCharacterLimit` is not sent; its image is an error saying so. `safe_mode` is the brain's toggle (on by default). The image model is the brain's own or the conversation's (T18, `imageModelOf`; `painterFor` is the one place it is chosen, for a turn, a regenerate, a retry, an edited prompt and an added one), and it is looked up **before** the brain is asked for a prompt, so an unknown model costs nothing (`unknown_model`, 400).
4. **The image.** `POST /image/generate` (JSON; `images[0]` is base64; 180 s timeout). The type comes from the bytes (`sniffImage`: PNG, JPEG, WebP, GIF), never from the format asked for. The bytes are written to `images/<id>.<ext>` through the vault (ciphertext for an encrypted user) **before** the record says `done`. `x-venice-is-blurred` / `x-venice-is-content-violation` become `blurred` / `contentViolation`. The model's list price (flat, per resolution, or per resolution and default quality) goes on the image and on `spentUsd` as soon as Venice has answered with an image; `/image/generate` reports no cost of its own. Live, the balance moved by exactly what was recorded. A failure becomes `status: "error"` with the message, and `image_error` carries `retry: {command: "image.retry", ...}`; the stream still ends with `done`, since the message is saved.
5. **An image is its own job (T05 triage).** Jason's play loop is: the painter paints, he sends the next turn to the GM at once, and the image fades in when it is ready. Every other brain needs only the prompt, which is in the ledger as soon as `image_pending` is said. So an image brain's **generation ends there**: the conversation's lock is released, and the image is made by a job of its own (`startPainting`, on its own `forkVault` key copy, so logout doesn't stop it, and it never waits on a client). The GM's turn can start while it paints; live, the GM answered before the image landed (T05 triage report). Until T05 triage the lock was held for the whole image (QA measured the GM refused for 2.7 s, and for 180 s with a frozen upstream).
   - **Tracked per image.** `images.ts` keeps, in memory, each image being made (`beginPainting`, inside the save of its pending record; `endPainting` after its final status is written), with its message and a `settled` promise.
   - **What waits for it**, with a 409 of its own code, `image_busy` (`assertImageIdle`, inside `mutateConversation` like `assertLedgerIdle`; T05 frontend gave it the code, so a client tells "wait for this image" from `conflict`, "a reply is being written", without reading words): what would replace or remove an image that Venice is already making and billing. That is an edit of the version's prompt and a retry of its image, the message's delete, and `conversation.delete`. **What doesn't:** turns by any brain, a regenerate of the message (a new version with its own image; the first lands in its own version), select-version, edits and deletes of other messages, brains, settings and templates. Edits of the prompt and `message.add` are still ledger edits, so they wait for a *reply* being written (`assertLedgerIdle`); `image.retry` doesn't (no brain sees anything new).
   - **Streams.** `turn` and `message.regenerate` of an image brain still stream to the end: `image_pending` (sent after the lock is released, so the client that hears it can go straight on), then `image_done` / `image_error`, then `done`. `generation.follow` replays them the same way when it attached before the prompt was saved. `image.retry` streams the same events. `message.edit` and `message.add` answer at once with `painting`.
   - **Following an image: `image.follow --conversation --message`.** It streams `image_pending` for each of the message's images being made, then `image_done` / `image_error` as each lands, and ends with `done` and the message as saved. With none being made it ends at once with the message as it is. It reads the message, waits for each pending image's job and reads again, so it can't miss a result that landed before it attached (T05 QA-2: `generation.follow` after an edit whose image failed instantly returned "nothing running" and left the client on "pending"). A client follows every pending image in its copy of the ledger with it: after a load, an edit, an add.
   - **Restarts (T05 QA-1).** On SIGTERM (`npm run up` / `down`) the server stops taking new work (`shutting_down`, 503), then waits up to 60 s for every generation and every image in flight to finish and save, before it exits; `scripts/proc.ts` waits 65 s before a SIGKILL. A restart mid-image used to lose the image Venice had made and billed. Only a crash or `kill -9` can still lose one, in which case the image is "interrupted" (below) and its cost is not recorded.
6. **Never pending forever.** A job adds its image to an in-memory set (`beginPainting`) before the pending record reaches disk, and removes it after the final status has. So a pending image that isn't in the set was being painted when the server stopped. `loadConversation` settles it on every read (`settleStaleImages`): **done, if its file made it to disk** (Venice made it and billed it, so it is kept), otherwise an `error` saying it was interrupted, to retry. The next write saves the settled status. An image recovered as done swaps in as a painted one does: its `previous` is dropped and that file deleted (T05 QA-4: it was kept, and the next replacement orphaned the file). Its cost isn't known there, so it isn't added; that needs a crash in the milliseconds between the file and the status write.
7. **Again.** `image.retry` paints the active version's prompt as it stands, with the image model and safe mode as they are now. A failed, interrupted, blurred or flagged image is replaced: like an edit, it stays as `previous` (if it was shown) until the new one is done. **A finished, clean image is never thrown away (T05 QA-5):** retrying it adds a new version with the same prompt (`repaintOf`: the version it repaints) and makes it active, so both paid images are kept and the pager goes back to the first. That is "the same prompt, another roll"; regenerate asks the brain for a new prompt instead.
8. **A timed-out image** says that Venice may still have made (and billed) it, not that Venice was unreachable (T05 QA-3): the client's timeout is its own error, not a connection failure.

**What other brains see doesn't depend on the image.** The prompt is the canon: every image message is framed (`otherBrainImage`) or rendered as the painter's own tool call whatever its image's status. So the default wording claims nothing about the picture (T07): `otherBrainImage` says only that the brain "called generate_image with this exact prompt", and `DEFAULT_TOOL.resultContent` that "the prompt was sent to the image model; the player sees the image once it is made". Both used to say the image "is now on the player's screen", which stopped being true when T05 triage let the next brain answer while an image paints. Conversations made before T07 keep the wording they have (it is theirs to edit).

## Hidden notes (T08)

Brains (and the player) can write text that every brain reads but the player sees only on purpose: a character sheet full of secrets (T10's Character Creator answers with nothing else), a GM's plans, what a clue really means. A note is a fenced code block whose info string starts with the word `hidden`:

````markdown
```hidden
Name: Sera Vane
Secret: she stole the second parcel
```
````

**It is folded, not secret, so hard rule 1 holds.** A note is ordinary ledger text: sent verbatim to every brain (a brain's own notes as its `assistant` text, everyone else's framed like any message), shown raw by `prompt.preview` and the payload view, edited raw in the message editor. Nothing in `buildRequest` knows about it. Only the human views fold it: the scrollback and the CLI's text output, to one line that says how big it is and never a word of it. Every brain sees every note, so a secret can still leak through a brain that mentions it; T10 accepts that (prompt craft keeps it rare).

**One rule, both clients: `src/conversations/hidden.ts`** (dependency-free, so the web imports it as it imports `wording.ts`; `web/src/api/types.ts` re-exports it). It is a line scanner that starts from Markdown's fenced code blocks and is **deliberately more eager to hide (T08 triage)**: a note that hides too much costs one click to open, a note that spills can't be unread. Its guarantee: **whatever Markdown (remark + GFM) would parse as a `hidden` code block, the scanner hides too** (a scratch fuzzer checked 190,000 random texts against remark in T08 triage, with no miss; the first, Markdown-faithful scanner missed about 1 text in 14, QA-1 and QA-2). So the browser's backstop below should never fire.
- **Opens:** a line that, after any quote markers (`>`), list markers (`-` `*` `+` `1.` `1)`), footnote labels (`[^1]:`) and indentation, is a fence of 3+ backticks or tildes followed by the word `hidden`, any case (```` ```hidden ````, `~~~Hidden`, ```` ````hidden ````). Not ```` ```hidden-notes ````, not mid-line. Otherwise it opens anywhere: at any indentation, with backticks in its label (```` ```hidden sheet for `Sera` ````, which Markdown refuses as a fence and would show as inline code), and **even inside another code block: the scanner doesn't track other code blocks at all**. A stray or unclosed fence earlier in the message (a `~~~` scene break, an indented ```` ``` ````, a code block the model forgot to close) would otherwise swallow every note after it and show it. The cost: an example of the convention inside a code block folds too.
- **Closes:** the same fence character, at least as many, nothing else on the line. Indented at most 3 columns, or as far as the opening fence if that is further, or 3 past the fence when a list marker starts the opening line (tabs count to the next multiple of 4): never further than Markdown would allow, so a note never ends before Markdown's block would. It may carry up to as many quote markers as the opening line, or none.
- **Unclosed:** it runs to the end of the message, **whatever happens to the quote or list it opened in**. Markdown ends a block with its quote or list item, so a note written carelessly (```` - ```hidden ```` with an unindented body, an unquoted line inside a quoted note) would end at its first line and show the rest; here the note runs on to its closing fence. A reply still streaming into a note, or cut off by `max_tokens`, looks exactly like this, so it is folded from its first line.
- **Inside a list or a quote:** folded in place (`> [Hidden · 1 line]`); the note's text loses the quote markers and list indentation where its lines have them.
- **Lines** end at `\n`, `\r\n` or a lone `\r`.
- **Code inside a note (the extra):** a fence with a word after it (```` ```js ````) inside a note opens a nested code block, and the note can close only after it does. Markdown would end the note at the inner block's bare closing fence and show the rest; for a note, that would spill it. A longer outer fence (```` ````hidden ````) or tildes also work, as in Markdown. A bare ```` ``` ```` inside a note still closes it (it can't be told from a closing fence), so a note that needs a bare code block uses one of those.
- **The label** (```` ```hidden GM plans ````) is the rest of the opening line. It is part of the note and the fold **doesn't show it**: live, a Character Creator told "the label is shown to the player, so never put a secret in it" labelled its sheet `Sheet: Sera Vane`, a name the player hadn't learned. A label still helps the brains, and anyone who opens the note sees it.
- **The fold's words** are `hiddenSummary`: `Hidden · 11 lines` (blank lines count, as in the raw text), `Hidden · empty`, and while a reply is still writing into it `Hidden · 3 lines so far` / `Hidden · being written`.

API: `splitHidden(text)` → `[{type: "text", text} | {type: "hidden", block}]` (joined back, the text exactly); `findHidden(text)` → the blocks (`start`, `end`, `prefix`, `label`, `body` without containers, `lines`, `closed`, `open` = unclosed, so running to the end of the text; always `!closed` since T08 triage); `foldHidden(text, marker?)`; `isAllHidden(text)` (a reply with nothing else, the Character Creator's); `isHiddenInfo(lang)`; `createHiddenFolder()` for streams; `couldOpenHidden(partialLine)`.

**The terminal.** `conversation.get`, `message.get` and `message.select-version` fold each text message's notes to `[Hidden · 5 lines]` (with the note's own quote or list prefix), and end with how to see them: `(2 hidden notes folded: ./sst conversation.get --id c_… --reveal shows them; --json has the raw text.)`. An image prompt is never folded: it is a plain caption in both clients. `turn`, `message.regenerate` and `generation.follow` fold as the reply streams (`createHiddenFolder`): text prints as it arrives, except an unfinished line that could still become an opening fence (`"``"`, `"> ```hid"`), which waits for its next character or its newline, and everything from an opening fence on, until the note closes and its marker prints. So a fence split across deltas never flashes a word. Whatever the split, the output joined is exactly `foldHidden(the whole reply)` (tested at every cut and on random splits). On a terminal, a dim `[Hidden · 3 lines so far]` line counts up meanwhile and the marker replaces it; after the reply, stderr says `message.get --conversation … --message … --reveal` shows it. **`--reveal`** (a CLI flag, like `--json`) shows everything as it is: a stream prints the reply as it comes, and a JSON command's text view gets the header `x-sst-reveal: 1`, which the adapter passes to `format(result, {reveal})`. `--json` is always the raw text. `prompt.preview`, `brain.list` and `setup.list` are never folded: they show what is sent. **Reasoning folds too (T08 triage, QA-3):** a stream prints `[Reasoning, folded: --reveal streams it; conversation.get --json has it]` once on stderr instead of the reasoning, as the browser shows it collapsed and `conversation.get` shows only its size. A brain that reads a character sheet reasons about its secrets in plain words, so streaming it spilled them in the terminal alone; `--reveal` streams it as before.

**The browser (T08 frontend).** Every text message, the player's and a brain's, saved or streaming, renders through `MessageText` (`web/src/features/chat/MessageText.tsx`): `messageParts(content)` (`web/src/lib/hiddenParts.ts`, DOM-free, so `test/web-hidden.test.ts` imports it) is `splitHidden` minus the blank gaps around a note. Each text part is Markdown; each note is a `HiddenNote` (`web/src/components/HiddenNote.tsx`): a dashed, faintly hatched bar with the shared words (`Hidden · 14 lines`) and a quiet "Show", never a word of the note or its label. A click, Enter or Space opens it in place: the label as a small caption (T08 QA-5), then `<Markdown text={block.body}>`, which is rendered only while open, so a folded note's words are never in the page at all, not even hidden in the DOM. Its header stays at the top of the scrollback while you read a long note, and folds it again. Nothing remembers an open note: a reload, another version (the pager) or a saved reply replacing its live twin starts folded.
- **Streaming.** The live reply (a turn, a regenerate in its message's slot, a re-attached `generation.follow`) re-splits on every delta: the note being written is the bar counting up (`Hidden · 3 lines so far`, shimmering), and a reply's notes can't be opened until it is saved (or has failed). The unfinished last line is held back while `couldOpenHidden` says it may still become an opening fence, as the CLI's folder does, so "```hid" never flashes as an empty code block before turning into the bar; a note the text already ends inside is the bar at once. A reply that is all note shows the typing dots, then the bar, never any text. The caret goes only at the end of the last Markdown part.
- **All note** (the Character Creator's): the badge and the bar, not "No reply text". A stopped or failed reply cut mid-note is its bar with the final count, openable.
- **In a list or quote:** the fold gets the item's marker (`2.`, `•`) or the quote's bar back, as the CLI keeps the prefix; the split ends the list or quote around it.
- **Opening and folding move nothing.** A note opens downward from its bar and the scrollback stays where it is, as it does for everything (see "Scrolling" under the web app); if the note runs off the bottom, "Latest" appears. The one scroll a note makes is on folding from its sticky header deep inside a long note: the note shrinks away above the view, so the scroll box brings the bar back to its top (16 px down), where you clicked, instead of leaving you past the rest of its message. (Until 2026-10-15 a context, `scrollPin.ts`, let an opening note get out of the scrollback's pin to the bottom; the pin is gone, and so is the context.)
- **The backstop:** `Markdown`'s code block renderer folds a block whose language passes `isHiddenInfo` with the same `HiddenNote`. The rule should never leave it one (T08 triage's guarantee).
- **Unchanged and raw:** the message editor, Copy, the payload view, image prompts (plain captions, never folded) and the settings panel (setup messages, system prompts: configuration, as `setup.list` and `brain.list`). Reasoning stays collapsed by default, mid-stream too.

Verified live in T08 engineer (2026-10-14), `deepseek-v4-1-flash`, reasoning off: a GM whose system prompt asked for its private plans in a ```` ```hidden GM plans ```` block wrote one (closed) before its narration, whose narration didn't give away the plan's names; a Character Creator asked for "nothing but one hidden note" answered with exactly one closed note of 11 lines, and the GM's next preview carried it verbatim, framed `<!-- from: Character Creator -->`.

## Dice rolls (T09)

Jason's loop: the player sends an uncertain action to a brain that names the odds ("Roll a d20: 15 or higher succeeds, 19 or higher is a hard success, under 15 fails"; T10's Show Me the Odds, or the Gilded Goat's Dice Master), then **rolls and sends the roll to the GM in one action**. The roll lands in the ledger as a message every brain reads ("🎲 I rolled a d20: **10**"), and the GM narrates the outcome the roll earned. Any brain can be sent a roll, image brains included, in every conversation.

- **The server rolls, never a model.** `rollD20()` (`src/conversations/dice.ts`) is `crypto.randomInt(1, 21)`: the OS's random number generator, with the rejection sampling that keeps every face equally likely. d20 only (Jason: "only D20s because that's easy"); `Roll.die` leaves room for more.
- **A roll is an ordinary player message.** Its text is the conversation's `roll` template with the number in it, and every brain reads it framed by the player template, like anything else the player says. Nothing in `buildRequest` knows about rolls. The version also keeps `roll: {die, result}`, display only (never sent), so a client can show it as a roll ("🎲 d20: 10", `rollLabel` in wording.ts).
- **The honor system.** Nothing guards a roll: edit it, delete it, regenerate the odds. Editing changes what every brain reads from the next request on, as any edit does; the version is marked `edited` and keeps the die's own `result`. **Once edited, the line is the roll** (it is what every brain was told), and the die's number is only history: `rollLabel(roll, edited)` says "🎲 d20 said 18" instead of "🎲 d20: 18", so `conversation.get` shows `🎲 d20 said 18 · edited` above "🎲 I rolled a d20: **3**" (T09 QA-1). No client shows an edited roll's `result` as the roll. That is information, not a lock.
- **The wording is a template (hard rule 1).** `templates.roll`, default `🎲 I rolled a d20: **{{roll}}**`, edited like the others (`conversation.update --templates.roll`, the browser's templates editor) and refused without `{{roll}}`. **It is applied once, when the server rolls:** the message holds the line it made, so a changed template shows in later rolls, and earlier rolls keep their text (edit those like any message). Why not render it at build time, as the framing templates are? Then a roll's text would be a number that only becomes words inside `buildRequest`, an edit would mean editing a number rather than the line the brains read, and every client would need to know the rule. As it is, a roll's `content` is exactly what every brain is sent (framed), like every other message. A conversation from before T09 gets the default on load (schema 3, `upgradeConversation`); a campaign file without `templates.roll` gets it too, and a version's `roll` comes along on import (a brain message's is dropped: only the player rolls).
- **Roll-and-send: `turn --roll`.** Lock → load → **roll** → plan (the roll's message goes after the player's text, if any, as a second player message, so the action comes first and its roll right after it) → open the Venice stream → save both messages in one write, and emit a `message` event for each (the roll's carries `roll` in its version), so a client shows the roll before `start` and the reply → the reply streams as in any turn. As with a turn's text, **nothing is saved, and the roll is never shown, unless Venice accepts the request**: a refusal up front leaves no roll behind (rolling again is the honor system's business). If the reply then breaks, the roll stays, and the retry is "send again with no new message and no new roll" (`turn --brain b_… without --content or --roll`); `details.retry` never rolls. A stop before any reply text says the same ("To get a reply, send again to … with no new message and no new roll: …"), since the up arrow would roll a second die (T09 QA-2; a typed message gets the "no new message" half). An image brain sent a roll paints from it as from any message.
- **Just roll: `message.roll`.** Adds a roll to the ledger as your message, asking no brain (`assertLedgerIdle`: refused while a reply is being written). Then `turn --brain X` with no content has X answer it.
- **The preview can't know the number.** `prompt.preview --roll` builds the same body with the roll's line left as the template has it, `{{roll}}` where the number will go, and its first note is `ROLL_PREVIEW_NOTE`: "The d20 isn't rolled yet. When you send, the server rolls it and puts the number (1 to 20) where {{roll}} is in your roll's line, the newest player message (a {{roll}} anywhere else is sent as written). The rest of this body is exactly what is sent." A sample number would look like a roll that had already happened; the placeholder is plainly not one, and it is the only difference (`test/dice.test.ts` puts the rolled number in the roll's line only, with a `{{roll}}` in the typed text that must stay, and `deepEqual`s the result with what the mock received; T09 QA-3). `planTurn(conv, {brain, content, roll: Roll | "unrolled"})` is the one function both use.
- **The terminal.** `turn --roll` prints `🎲 d20: 14` on stderr when the roll's `message` event arrives, before the brain's header and reply (stdout stays the reply alone). `conversation.get` and `message.get` put `🎲 d20: 14` in the message's header line, above its text. `message.roll` prints the roll and how to have a brain answer it.
- **For the browser (Frontend pass).** `turn` takes `roll: true` with every send (the big Send and each brain's chip), with or without text. The roll arrives as a `message` event (after your text's, if any) before `start`; `useChat` already upserts each one, so it shows at once. Show a version with `roll` as a roll, apart from typed lines: the die and `rollLabel(roll)` ("🎲 d20: 14", re-exported from `web/src/api/types.ts`), with its `content` (the template's line, Markdown: what the brains read). **An edited roll (`edited`) is different (T09 QA-1): its `content` is the face, since it is what every brain was told, and `roll.result` must never appear as the roll (not on the die, not as the label).** The die's own number may show only as quiet history beside the "edited" mark, worded by `rollLabel(roll, true)` ("🎲 d20 said 12"), as the CLI's header does. Edit and delete work as for any message. The template is the fifth row of the templates editor (`roll`, needs `{{roll}}`, and says it applies to the next roll). The payload view previews a roll with `prompt.preview --roll` and shows `ROLL_PREVIEW_NOTE` from `notes` like any note. Built in T09 frontend: see "Web app", *Dice rolls*.

Verified live in T09 engineer (2026-10-14), `deepseek-v4-1-flash`, reasoning off, on a clone of the Gilded Goat (encrypted `dev-` user, the example's prompts unchanged): the GM answered a lie with "That's a Deception check."; the Dice Master, asked "What do I roll?", answered "**Deception check:** roll 1d20 + 5, DC 14"; `turn --brain "Game Master" --roll` rolled 18 and the GM narrated her believing the courier story (18 + 5 ≥ 14). Then the roll was edited to "🎲 I rolled a d20: **3**" and the GM's reply re-rolled: she saw through it ("No, you're not"), awkwardly but not disastrously, as the GM's prompt asks. Four text calls, $0.0017.

## Pinned messages and brains that make brains (T16)

Jason's problem: one Character Actor played every character, so by message 50 its history held Alice, Bob, Charlie and Dave as its own `assistant` lines, and Alice's sheet was 45 messages back behind three rival sheets. Going back to Alice confused it. The fix: **every character gets a brain of their own, made when the Character Creator writes their sheet, with that sheet pinned at the top of its view.** Alice's lines are then her own `assistant` turns, Bob's are framed `<!-- from: Bob -->`, and her sheet is always right under her instructions. **Nothing in the code knows what a character is**: these are three generic pieces, and a Place Creator whose replies make `Place {{n}}` brains works the same way (`test/makers.test.ts` has one).

### Pinned messages

- **A pin is a link, not a copy** (`Brain.pins: [{messageId, as}]`). In the pinned brain's requests the message is sent right after the setup messages (step 2b of "Prompt assembly"), in ledger order, and not again at its place; every other brain still sees it where it is. Editing the message, re-rolling it or picking another version changes what the brain gets from its next request, because the builder reads the message's active version as it stands.
- **How it is sent (`as`), every word visible:** `ledger` (the default): exactly as at its place from that brain's point of view, framed with its author's name, or the brain's own `assistant` words, just moved up (no new wording at all). `system`: its text, verbatim, as a system message. `assistant`: its text, verbatim, as the brain's own words. The payload view says which message is pinned and how (`pinnedNote`), `prompt.preview` returns where each went (`pinned`), and its text marks those messages ("pinned m_…, as it appears in the ledger").
- **Any message to any brain, any time** (`brain.pin --brain --message [--as]`, `brain.unpin`). Pinning changes a brain's next request, not the ledger, so it isn't refused mid-reply. Deleting the message removes every pin of it (below).

**Why `ledger` is the default (live probes, 2026-10-15, `deepseek-v4-1-flash`, reasoning low, `stream: false`, nothing saved).** At a harbor tavern with two characters (the hooded figure's sheet written by the Creator; a barkeep's sheet whose secret is that he has just sent the potboy to the watch), each character's brain was asked the same question three times, its sheet pinned as `ledger`, `system` and `assistant`: the figure, "The barkeep keeps watching this table. Has he sold you out already?"; the barkeep, "Why are they so interested in this place tonight, friend?". **All six held**: first person, the right name, the sheet's tells (the brass button, the nudged cup, the tankard and the eye on the door), and neither leaked the other's secret (the figure's reasoning under `assistant`: "She doesn't know the watch is already summoned"). The roles made no difference we could see, so the default is the one that adds no wording and keeps who wrote the sheet visible; the other two stay a choice per pin, for Jason to try on a long campaign. (DeepSeek seems to hoist system messages to the top, T13, so `system` effectively joins the brain's instructions.)

### Brains that make brains

- **The setting** (`Brain.makes`, "Each new message makes a new brain"): a **name pattern** with `{{n}}` (`Character {{n}}`), a counter (`next`), how the message is pinned (`pinAs`), and a **blueprint**: the new brain's kind, system prompt, final reminder, reasoning, stop sequences (and for an image blueprint, safe mode, shape and tool text, filled as a new image brain's are, so `brain.list` shows every word; T16 QA-2): everything `brain.add` takes but its name and color. `--no-makes.enabled` keeps it and makes nothing; `--makes null` removes it.
- **When.** Every **new message** the maker gets in the ledger: a generated reply (a stopped one too, since it is saved), or one written with `message.add --as <maker>` (text or, for an image maker, a prompt). **In the same write** as the message (`appendMessage`, `src/conversations/makers.ts`, the one way a new message goes in, called inside `mutateConversation`), so a crash can't leave one without the other. A failed reply saves nothing and makes nothing. **New versions never make another brain** (regenerate, steer, fresh take, edit): the pin follows the active version, so the same character just changes. Moving a message to the maker (`message.set-author`) is not a new message either.
- **What it makes** (`makeBrain`): a brain from a copy of the blueprint (its own words from then on, edited like any brain's), the next free color, `madeFrom` the message, the message pinned `pinAs`, named from the pattern with the counter. The counter counts up, so renaming "Character 1" to "Alice" never makes another "Character 1"; a name already taken (a brain called "Character 4" by hand) is skipped. **It steps back once when the newest made brain goes** (T16 QA-8, `freeNumber`): deleting a slip (the message, and the never-spoken brain it made with it), or `brain.delete` of that brain, while it still has the name the newest number gave it, frees that number, so undoing a slip leaves no gap. A renamed or older brain changes nothing. A pattern whose names would look like brain ids (`b_{{n}}`) is refused when set, as one without `{{n}}` is (T16 QA-3). A new message by a maker whose reply was made this way is announced in the stream: `{type: "brain_made", brain, messageId}`, after the save and before `done` (an image maker's: before `image_pending`, where a client stops reading); `generation.follow` replays it; `message.add` returns `made`; `generation.stop` returns `made` when the stopped reply made one. The CLI says it after the reply, with the rename command.
- **The payload view says so** before you send (`makesNote`): "Character Creator makes a brain from each new message: this reply will make a new brain, Character 4, …", since it is a side effect of sending.
- **By hand: `brain.make --message [--name]`.** The same result for a message that already exists: its author's blueprint (on or off), the next name (or `--name`, which doesn't use a number), the message pinned. This is how Jason moves a campaign whose sheets were written before the setting existed: give the Creator the setting (`brain.update --makes …`, or `brain.import` the preset's Creator, which brings it), `brain.make` each old sheet, rename each brain, then move the old Actor's lines with `message.set-author`. A message that already made a brain still here makes no second (409: pin it to another brain instead).
- **A maker can't decline.** Any new message makes a brain, whatever it says, so "no one new here" from a maker is a brain too. Considered and left out in T16 triage: a generic way out (say, "an empty message makes none", or a per-maker "only when the message contains …"). A model can't reliably answer with nothing, an empty *stopped* reply is better off with its brain (a re-roll then fills the pinned message), and a condition is a new field to show and edit everywhere for one prompt's sake. The preset's Creator always has someone to write instead (below), and undoing a slip is one `message.delete`, which takes the never-spoken brain with it and hands back its number.
- **Deleting the message** deletes the brain it made, in the same write, while that brain has never spoken (and isn't the default): it was only ever that message's brain. If it has spoken, it stays with its lines and loses only the pin; other brains' pins of the message go too. `message.delete` says which brain lost what.
- **Campaign files.** A brain in a file takes `pins` (by the messages' `id` in the file), `makes` (checked as `brain.update --makes` checks it) and `madeFrom`; messages take an optional `id` for them to point at. Import and clone give everything fresh ids and re-point pins and `madeFrom`. **Without the ledger (`--without-messages`) a brain made from a message stays behind with it** (its prompt is about a pinned message that isn't coming; T16 QA-4), the other brains come without pins, and each maker counts from 1 again: a fresh start on the same kit. (If that would leave no brain at all, they all come.) A clone `--through` a message (2026-10-20) applies the same rule to the messages after it: a brain made from one of them stays behind (unless it speaks in what comes), pins of them go, and each maker hands back the left-behind brains' numbers (`freeNumber`, newest first). `brain.import` brings a maker's setting whole (the preset's Creator makes characters in any conversation) but not pins, which name that file's messages; its notes say so. `presets.list` / `examples.list` give a maker's pattern (`makes`).

## Presets (T10)

A **preset** is a ready-made kit of brains with good default instructions and no world: no World Bible and no story. Jason's two uses: start a campaign from one ("Chinatown, film noir": pick the tabletop preset, write the World Bible, play), and drop any one of its brains into a conversation he already has.

- **A preset is a campaign file (T07) with no setup and no messages**, committed in `presets/<name>.json` and edited in the repo like `examples/`. It is read and checked by the same `parseCampaign` + `toConversation` as an example. A file with setup or messages is refused, where it is listed and wherever it is used ("a preset has brains and no world… A campaign with them belongs in examples/"). **Why a folder of its own**, not examples with a flag: the two answer different questions (an empty world to fill, against a campaign ready to play), the browser offers them apart, and each list stays plain. Nothing new is in the file format except `about` on a brain.
- **`about` on a brain** (campaign files: presets and examples alike) is one line on its job, for `presets.list`, `examples.list` and the browser's pickers. Like the file's own `about`, it is never sent and never stored. Both are one line: a line break is refused (T10 QA-7).
- **The lists check what an import checks** (T10 QA-7): each file goes through `parseCampaign` and `toConversation`, so a file an import would refuse (two brains of one name) is listed as unusable, with why.
- **`presets.list`** (no login) → `{presets: [{name, title, about, brains: [{name, kind, color, about, reasoning?}]}]}`. Each brain is listed as an import would make it: its color (the one `nextColor` would give a brain without), and `reasoning`, its effort, only when the file switches reasoning on (T10 frontend: a labeled opt-in, so the pickers tag it "reasoning low"). `examples.list`'s brains have the same shape.
- **`conversation.import --preset <name> [--title]`**: the preset's brains, settings and templates; no setup, no messages. The CLI's text for any import or clone that has no setup ends with a pointer to `setup.add`, since every brain reads the World Bible.
- **`brain.import --conversation (--preset <name> | --example <name>) --brain <its name in the file> [--name <new name>]`**: one brain, whole (system prompt, reminder, kind, reasoning, stop sequences, tool text, safe mode), exactly as an import of its file would make it (the whole file is checked). It gets a fresh id, is never the default, and keeps its color unless a brain there already has it (then `nextColor`). A name clash is `brain.add`'s 409 (`checkName`), whose message gives the way out ("Add this one under another name with --name"). **Nothing else comes over**, and the answer's `notes` say so: when the file's templates differ from the conversation's (naming which); for an example's brain, that its prompt was written for that campaign; and, for a preset's brain going into a conversation with a brain whose prompt doesn't know hidden notes (no ```` ```hidden ```` in it, as the Gilded Goat's), that it learns secrets only from hidden notes, never from another brain's system prompt, and that a hidden note in a setup message shares one (T10 QA-3: the imported Actor played the Goat's shy, flustered figure cool and firm, because her secrets live in the Goat GM's prompt). The Goat itself is unchanged: moving its secrets into a shared note would hand them to its Joke Teller and painters, which weren't written to keep them. `→ {conversationId, brain, from: {preset | example, title}, notes}`.
- **Templates.** The Tabletop RPG preset uses the default templates, and its prompts don't lean on them: they name the human "the player (the user)", so `<!-- from: the user -->` and the Gilded Goat's `<!-- from: the player -->` read the same. A preset brain dropped into any conversation therefore reads the table as it would in the preset, and the add's note is only information.

## Models (2026-10-14; a file you edit since T19)

Venice lists ~130 text and ~45 image models, and the app can use most of them: any model Venice lists can be set by id (`conversation.update --settings.text-model`, `--settings.image-model`, and since T18 a brain's own, `brain.update --text-model`, `--image-model`), and `models.list --all` shows them all. **Which ones `models.list` (and so the browser's pickers) offers is a file (T19, 2026-10-21): `models.ini` in the project folder, gitignored, or, when there is none, the committed `models.example.ini`.** So a fresh clone runs with no setup step and offers exactly the example's models, and nobody's own list is committed.

## Command surface

Commands live in one registry. Each has a name, a zod args schema, an optional `stream: true`, and a handler. Two adapters expose them:

- **HTTP:** `POST /api/<command>` with a JSON body of args. Non-stream commands reply with JSON. Stream commands reply with NDJSON (`application/x-ndjson`), one event per line. Binary commands (image fetch) also answer `GET /api/<command>?...` so `<img src>` works.
- **CLI:** `./sst <command> --arg value ...`. This is a thin HTTP client over the same endpoints. `--content @file.md` reads a file and `--content -` reads stdin. `--json` prints raw JSON. Stream commands print text deltas live.

Stream event shapes (NDJSON):
`{type:"following", startedAt}` (`generation.follow` only, first: a reply is running) · `{type:"message", message}` (a player message saved; T09: a `turn --roll` sends one for your text, if any, then one for the roll, whose version has `roll`) · `{type:"start", brainId, brainName, messageId, regenerate?, steer?, model?, ownModel?, conversationTitle?}` (T07 triage: `turn` and `message.regenerate` add the conversation's title, which the CLI prints when `SST_CONVERSATION` chose it; T18: and the text model the reply is written with, `ownModel` when it is the brain's own) (the id the new brain message will have, so a UI can key its streaming bubble; for `message.regenerate`, the id of the message getting a new version, with `regenerate: true` and its steer, if any, or its `thought` (T17: no head `delta` any more; the note came first as `muse_note`). T05 adds `kind: "text" | "image"`, and `imageOnly: true` for a generation that only paints: `image.retry`, or the image an edit or add started) · `{type:"reasoning", delta}` · `{type:"delta", delta}` · `{type:"prompt", delta}` (T05, replacing the planned `tool_args`: an image brain's prompt as it streams, decoded from its tool call's arguments) · `{type:"muse_note", message, before, brain, brainCreated?}` (T17: a fresh take's Muse note was saved, right before `before`; `brain` is the Muse, `brainCreated` when this fresh take added it; before `start`) · `{type:"brain_made", brain, messageId}` (T16: the reply just saved made a brain, its author being a maker; after the save, before `done` or `image_pending`) · `{type:"image_pending", messageId, imageId, model, message}` (the prompt is saved; `message` has the pending image) · `{type:"image_done", messageId, imageId, image, message}` · `{type:"image_error", messageId, imageId, error, image, message, retry}` (the message is saved, its image isn't; `retry` is the `image.retry` request; the stream still ends with `done`) · `{type:"done", message, note?, spentUsd?}` (`note` is a one-line summary such as `Assistant · 52 in / 34 out · $0.000056`, which the CLI prints to stderr; `message` is `null` only from `generation.follow` when nothing was running (`image.follow`'s `done` always carries the message as saved); `spentUsd`, from `turn` and `message.regenerate` since T03 frontend, is the conversation's running total once this reply's cost was added, so a UI shows it without re-reading the conversation) · `{type:"error", error: {code, message, details?}}` (a reply whose stream broke, `venice_error` from `turn` or `message.regenerate`, carries `details.retry`: the exact request that retries it, `{command: "turn", args: {conversation, brain}}` or `{command: "message.regenerate", args: {conversation, message, steer?, thought?}}`, type `RetryRequest` in `types.ts`, T04 QA-1)

Every stream ends with exactly one `done` or `error` event; the CLI treats anything else as a broken stream. The CLI prints `delta` and `prompt` to stdout as they arrive and `reasoning` (folded to one line unless `--reveal`, T08 triage) and status lines to stderr, so `./sst turn ... > reply.md` captures only the reply (for an image brain, its prompt). An `image_error` makes the CLI exit 1.

### HTTP contract (implemented in T01, `src/server/app.ts`)

- `POST /api/<name>` with a JSON object body (an empty body means `{}`) and `Content-Type: application/json`, which is required even when the body is empty; anything else gets a 415 `unsupported_media_type`. With curl, add `-H 'content-type: application/json'`. Args are validated with the command's zod schema in strict mode, so unknown keys are a 400.
- Success: the JSON result, status 200. Failure: `{"error": {"code", "message", "details?"}}` with a real status: 400 `bad_args`/`bad_json`, 401 `unauthenticated`/`wrong_password`/`session_ended`/`session_expired`, 404 `not_found`/`unknown_command`, 405, 409 `conflict`, 502 `venice_error`, 500 `unreadable_file` (a damaged or foreign file, named with the reason), 500 `internal` (whose details go only to the log).
- Stream commands: the adapter pulls the first event *before* sending headers, so a failure up front (unknown id, 409 busy) is a normal HTTP error rather than a 200 stream with an error inside. After that, it keeps draining the generator even if the client disconnects, so work finishes and persists. **The work never waits on the client (T02 QA-2):** writes to the response are queued, never awaited, and once the request's signal says the client has gone they stop. A client that left before the response started is never read from or cancelled by @hono/node-server, so an awaited write there blocked forever and kept the 409 lock and the request's key copy until a restart. Handlers that should stop on disconnect can watch `ctx.signal`.
- `GET /api/<name>?k=v` works only for binary commands (so `<img src>` works) and `health`. State-changing commands can't be triggered by a link. Query values arrive as strings.
- Local-only guard: requests whose `Host` isn't `localhost`, `127.0.0.1` or `[::1]` are refused (DNS rebinding), and so is any request with a non-loopback `Origin` (CSRF). The Vite dev server on another localhost port is still allowed. Pages on *other* localhost ports are stopped by the JSON requirement instead: without a CORS preflight a page can only send `text/plain` or form bodies, and the server never approves a preflight (it sends no CORS headers), so a blind cookie-carrying POST from, say, `localhost:3000` gets a 415 (T01 QA-4).
- `x-sst-cli: 1` asks for `{result, text}`, where `text` is the command's own `format()` rendering. The CLI uses it; the browser doesn't need it. With it, `x-sst-reveal: 1` (`./sst --reveal`, T08) asks that rendering to show hidden notes instead of folding them.
- Everything else under `GET /` serves `web/dist` with an SPA fallback to `index.html`, or a placeholder page when there's no build.

### Writing a command

`command({...})`, `streamCommand({...})` or `binaryCommand({...})` from `src/registry.ts`, registered in `src/commands/index.ts`. Each one has a `name`, a `description` (the first line is the summary in `./sst help`), a zod `args` object, `auth` (default `true`, meaning login required) and optional `examples`. JSON commands can add `format(result, {reveal})` for CLI text (`reveal`: the CLI's `--reveal`, T08; fold hidden notes unless it is set). Mark a password-like arg with `.meta({ secret: true, prompt: "Password for {username}: " })` and the CLI prompts for it with hidden input when it's omitted (`confirm: true` asks twice); `.meta({ ask: true, prompt })` asks in the clear (a confirmation, T06). With no terminal, it reads the first line of stdin, and empty stdin is a usage error rather than an empty password. A secret flag value is literal, except that `-` reads stdin: no `@file` expansion. `ctx.requireSession().vault` is this request's own key copy, valid until the handler (or the stream) finishes. Don't name args `json`, `help`, `out`, `open` or `reveal`, since those are CLI global flags. The catalog the CLI parses flags from is `help`, which returns each command's JSON Schema.

## Web app (`web/`)

React 19 + Vite + Tailwind v4, dark only, built to `web/dist` by `npm run up` and served by the same server. It is a skin over the commands: every server call goes through `web/src/api/client.ts` to `POST /api/<command>` (or `GET` for a binary command's `<img src>`), typed by the command maps in `web/src/api/types.ts`. There are no UI-only endpoints and no other fetches.

- **Errors.** Every failure is an `ApiError {status, code, message}`: the server's own error body, or `network`, `stream_broken` or `bad_stream` from the client. `status` is 0 when there was no HTTP error status. Views show `message` inline where it happened, or as a sticky error toast.
- **Streams.** `api.stream()` yields each NDJSON event as its line completes. A server `error` event, a dropped connection and a stream that ends without `done` all throw, so a consumer keeps the text it already has and still sees the failure. Aborting stops reading only; the server finishes and saves anyway.
- **Types.** The conversation document and model types are the server's own (`import type` from `src/conversations/types.ts` and `src/venice/models.ts`, both dependency-free), so the UI can't drift from what is on disk. Command args are still written out in `web/src/api/types.ts`.
- **Chat view (T02).** `/` is the new-conversation form and `/c/<id>` the chat. `features/chat/useChat.ts` holds one conversation: the ledger as saved, plus at most one *live reply* (streaming, or failed with its partial text). `turn` and `generation.follow` share one event reducer; deltas are buffered and painted once per animation frame. On load (and when the tab regains focus) it calls `conversation.get` then `generation.follow`, so a reload mid-reply picks the stream back up where it is. Leaving the view only stops reading. A 409 on send shows the error, gives the text back to the composer and follows whoever is replying (another tab, the CLI). Unsent drafts live in memory only, never in browser storage (an encrypted user's text must not land on disk).
- **Scrolling (2026-10-15, Jason: "just use the browser default").** `Scrollback` scrolls by itself once: a conversation opens at its end (`ChatView` is keyed by the conversation, so a mount is a new one), and stays there while what is on screen settles (a picture taking its own shape, a reply re-attached after a reload) until you scroll, click, type or touch, or 1.5 s pass. From then on nothing moves the box but you and two buttons. New text, your own sent message included, comes in below and runs off the bottom; an editor, a steer box or a note grows in place; the browser's own scroll anchoring (`overflow-anchor`, left on) keeps what you are looking at still when something above it changes height. The round **Latest** button shows whenever more than 64 px is below the view (on scroll, and when the content grows under a still box) and scrolls to the end on a click; the "X's picture is ready ↑/↓" pill scrolls to the card on a click. This replaces the T07–T14 pin to the bottom (stuck within 96 px, re-pinned on every render and resize, with exceptions for typing, sending and opening notes), which could yank you to the bottom when you stopped scrolling just above it.
- **Message actions (T03).** Each message (`features/chat/MessageItem.tsx`) has copy, edit and delete; a brain message with versions has the `‹ 2/3 ›` pager (always shown, since it is state); the last brain message has **Regenerate**. ## Mock Venice

`src/dev/mock-venice.ts` is a small HTTP server that speaks the Venice protocol: `/models`, `/chat/completions` (SSE streaming, including reasoning and forced tool calls), `/image/generate` (a tiny real image) and `/api_keys/rate_limits`. `npm run up:mock` starts it on port 4748 and points the app at it with `VENICE_BASE_URL`. In mock mode the server never loads `.env`, so the real key can't reach the mock. Tests start it in-process with `startMockVenice({ port: 0, delayMs: 0 })`.

Mock replies are deterministic and echo structure: `MOCK reply to brain "<system prompt, first 30 chars>"; saw N messages; last: "<last message, up to 60 chars>"`. A longer last message shows its first 30 and last 29 characters around `…` (T03), so a steer's instruction, which comes at the end of the steer template, shows in the reply. QA can then confirm what each brain saw without spending money. Because a reply echoes its input, a steered mock version quotes its own steer; checking "no trace of the steer" against the mock means checking the roles and the non-assistant messages, not grepping the whole body. Automated tests always use the mock or pure functions, never the live API.

Implemented in T01:
- The model list is a handful of entries copied verbatim from the live `/models` response (`src/dev/mock-models.ts`), including every model `models.example.ini` enables, so a fresh clone's mock mode offers what live mode does: `deepseek-v4-1-flash` (reasoning effort), `google-gemma-4-31b-it` (reasoning effort with "medium", T19), `venice-uncensored-1-2` (no reasoning), `z-ai-glm-5-3` and `abliteration-abliterated-model-large-v2` (reasoning with no effort levels, so reasoning off is `disable_thinking`; with the example's list, `models.list` shows them only with `--all`), and four image models, one per way of sizing and pricing an image: `z-image-turbo` (width × height, flat), `krea-2-turbo` (resolution and aspect ratio, per resolution), `hunyuan-image-v3` (aspect ratio only, flat) and `grok-imagine-image-2-0` (per resolution and quality). (2026-10-14: `gemini-3-6-flash` and `nano-banana-2` went, being anonymized.)
- Chat streams match the live wire format captured on 2026-10-13: a role chunk, `reasoning_content` deltas (when the model reasons and `reasoning_effort` isn't `"none"`), `content` deltas or `tool_calls` argument fragments, a `finish_reason` chunk, then, with `stream_options.include_usage`, a final chunk with `choices: []`, `usage` and `cost: {usd, diem}`, then `data: [DONE]`. `stream: false` returns a plain `chat.completion`. For models without reasoning, the role chunk is `{role: "assistant", content: ""}`, as it is live.
- `max_tokens` is honored, counted in words, reasoning first and then content, as live: the reply is cut, `finish_reason` is `"length"`, and the last content delta rides in the finish chunk. A small budget with reasoning on leaves no content at all, like live (T02 QA-6).
- It **rejects** chat requests without `venice_parameters.include_venice_system_prompt: false`, so a regression on that hard rule fails tests.
- Images are always PNG, whatever `format` asks for, with the size taken from `width`/`height`, or from `aspect_ratio` for the resolution-sized models, scaled down to at most 256 px a side in the asked shape (T05 frontend; each side used to be capped on its own, so 1216×832 came back square); the app sniffs the type (T05). The picture is a soft two-color gradient chosen by the prompt, so different prompts look different in the browser. `return_binary: true` returns raw bytes. Image responses carry `x-venice-is-blurred` and `x-venice-is-content-violation`, like live: `false` unless the prompt says `MOCK_BLURRED` (with `safe_mode` on; the image comes back grey) or `MOCK_VIOLATION`.
- T05 triggers. Chat: `MOCK_TWO_TOOL_CALLS` (two parallel calls, fragments interleaved by `index`), `MOCK_NO_TOOL_CALL` (ignores `tool_choice`, answers in text), `MOCK_RUNAWAY` (T18 QA-2: ignores it and repeats one sentence for ~8,600 characters, as Mistral Small 3.2 once looped). Image (in the prompt): `MOCK_IMAGE_ERROR` (400), `MOCK_IMAGE_FLAKY` (503 the first time a prompt is asked for, fine after: for retry), `MOCK_IMAGE_SLOW` (`imageSlowMs`, default 2 s, `MOCK_IMAGE_SLOW_MS` for `npm run up:mock`, to watch a pending image or reload mid-paint by hand; the prompt itself streams at normal speed). A mock tool call's prompt quotes the first 60 characters of the last message, so an image trigger in your message reaches the image request, for a brain whose reminder is off. `max_tokens` also cuts tool-call arguments (counted in their 12-character pieces) with `finish_reason: "length"`.
- A mock balance starts at $10 and goes down by each call's computed cost.
- `GET /_mock/requests` returns the last 20 request bodies, newest first. Compare it with `prompt.preview` to prove the real send matches the preview.
- Triggers in the last message (chat) or the prompt (image): `MOCK_ERROR` returns an HTTP error (`MOCK_ECHO_ERROR`, 2026-10-20: a 400 that quotes the last message, for the failure diagnostics' masking), `MOCK_SLOW` makes it slow (useful for 409 and stop tests), and `MOCK_MIDSTREAM_ERROR` drops the connection halfway through. `MOCK_MARKDOWN` (T02 frontend) appends a long Markdown reply after the echo line (`src/dev/mock-markdown.ts`: headings, nested and task lists, code in three languages, an aligned table, nested quotes, a footnote, an HTML comment), about 7 s at the default delay, which is also long enough to reload mid-stream.
- T08: `MOCK_HIDDEN` answers with the echo line, a hidden note (a made-up character sheet in a ```` ```hidden character sheet ```` block, with `MOCK_SECRET` in it) and a visible line after it; `MOCK_HIDDEN_ONLY` answers with one note and nothing else, the echo line inside it (the Character Creator's shape). Both stream in 3-character pieces, so the fences arrive split across deltas, as they can live. `max_tokens` (counted in those pieces) cuts one mid-note, which leaves it unclosed.
- T07 triage: `stop` is honoured, as live: a reply's text ends just before the first stop sequence in it, with `finish_reason: "stop"`. The echo line itself is exempt, since it quotes the last message, framing and all. `MOCK_IMPERSONATE` adds a fake `<!-- from: Dice Master -->` line and a roll after the echo, which a brain's default stop sequence cuts.
- T04: triggers are read from the **last message**, which for a brain with a final reminder is the reminder, not your message. To slow down or break a reply from such a brain, put the trigger in its reminder, or turn the reminder off for the test.
- T02: it also refuses a chat request whose first message isn't a non-empty `system` message (hard rule 1). `MOCK_SLOW`'s per-chunk delay is `slowDelayMs` (default 250 ms; tests use 20). `MOCK_MIDSTREAM_ERROR` waits for what it wrote to reach the client before dropping, so even with no delay it is a real mid-stream failure.
